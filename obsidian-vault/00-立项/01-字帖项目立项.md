# 字帖项目立项文档

> 状态:已立项 | 日期:2026-08-10 | 决策人:唐正涛(我拍板)

## 一、产品定义

一句话:一个开源的"对话式字帖生成器" — 输入一句话("一年级上册第五课,米字格,带笔顺拼音"),直接生成可打印的 PDF 字帖。

- 定位:部编版教材同步的练字内容服务,工具只是手段
- 目标用户:小学生家长(90% 在手机微信里操作)、语文老师
- 核心场景:老师在家长群布置"今晚练第5课生字" → 家长打开工具 → 一句话拿到字帖 → 打印
- 开源模式:核心生成器 + 数据全开源,GitHub 社区共建;不做闭源工具站

## 二、为什么做(竞品格局调研 2026-08-10)

| 竞品 | 模式 | 弱点 |
|---|---|---|
| E字帖 nqez.com | 几十种模板,免费+会员 | 2013年风格 UI,移动端差,纯表单 |
| 小帆船字帖 zi.ixfc.net | 微信生态,VIP 99-149元/年 | 已证明微信变现跑得通,但体验老旧 |
| 淡墨水 danmoshui.com | 极简个人站,3个功能 | 无运营无移动端 |
| 爱汉字 2hanzi.com | 部编版同步生字表,查表式 | 静态列表,非生成器,无内容运营 |

结论:竞品全是"输入文字→出字帖"的裸工具,**没有一家**做"自然语言一句话生成";教材同步有人占位但做得糙;AI 对话式生成在字帖领域是空白。

## 三、技术栈决策(纯项目角度,已排除学习路线因素)

**TS 全栈**。理由:
1. 开源项目生命线是贡献者,一门语言全栈 = 贡献门槛最低,类型前后端共享
2. Vercel AI SDK 是 AI 应用事实标准:流式聊天 + generateObject + zod 结构化输出
3. DeepSeek/Qwen/Ollama 全有 OpenAI 兼容接口,一个 provider 接住,本地小模型也能跑
4. Node 部署轻(镜像 100MB 级),阿里云香港 47.76.47.229 直接跑

### Spike 验证记录(2026-08-10,消除 PDF 风险)

- pdf-lib + 楷体 TTF 嵌入:✅ 11MB 楷体 → 6.8KB PDF(子集化生效),文本层提取正常无乱码
- pdfkit:✅ 7KB,同样全绿
- 坑:pdf-lib 的 `registerFontkit` 是**实例方法**不是静态方法;字体包用 `@pdf-lib/fontkit`(官方 fork,不要用 fontkit 2.x,有兼容问题)

### 技术栈清单

- 后端:Node.js + TypeScript(轻框架,解析器/引擎为纯 TS 模块,零框架依赖)
- AI 层:Vercel AI SDK(@ai-sdk/openai-compatible → DeepSeek/Qwen/Ollama)
- PDF:pdf-lib(轻、子集化内置),复杂排版再上 pdfkit
- 前端:Vue3 + Vite + @ai-sdk/vue(流式聊天)
- 数据:JSON 数据包随仓库走(生字表/笔顺/模板),不做数据库
- 字体:OFL 免费商用楷体(候选:寒蝉拙楷、演示春楷/秋楷、法华文楷),禁止 simkai(微软版权)
- 部署:Docker Compose → 阿里云香港

## 四、架构分层

```
┌─ Vue3 聊天前端 + PDF 在线预览
├─ LLM 解析层(AI SDK,自由表达→结构化参数,可插拔 provider)
├─ 规则解析器(正则+数据表,"一年级上册第五课"这种结构化输入零 LLM 直接解析)
├─ 字帖引擎(纯 TS:参数→PDF,可独立被其他项目引用)
└─ JSON 数据包(生字表/笔顺/模板)+ OFL 楷体子集
```

两个关键设计(开源项目生死线):
1. **零门槛可跑**:规则解析器优先,LLM 只是增强。没有 API key 的贡献者 clone 下来就能跑,响应快、可离线
2. **数据即代码**:生字表/笔顺/模板是版本化 JSON 随仓库走,贡献者 PR 就能更新数据,star 增长靠社区内容
